# Улучшение надежности: этап 1

Реализовано:
- В ключах внешних URL сохраняются параметры содержимого. Удаляются только известные tracking-параметры и fragment. Публичные URL статей не меняются.
- Числа, порядок счета и отрицания защищают новости от автоматического отсечения при изменении фактов. Это консервативная эвристика, а не семантическая модель событий.
- При ingestion учитывается сохраненный полный текст; кандидаты текущей партии не сравниваются дважды.
- Перед каждой публикацией повторно проверяются статьи всех категорий за последние 48 часов, включая публикации текущей партии.
- Ручная и автоматическая публикация используют общую PostgreSQL-блокировку.
- Статья, запись ленты, статус черновика и статус плана сохраняются одной транзакцией. Исправлено чтение статьи до создания записи ленты.
- Незавершенные очереди не ограничиваются последним ingestion. Существующий лимит возраста enrichment (48 часов) и размеры партий сохранены.
- CI запускает регрессионные тесты и интеграционные тесты PostgreSQL.

Вызовов AI API этот этап не добавляет. Обработка ранее пропущенного остатка может увеличить общее число обработанных материалов. Размеры партий и бюджет web search не повышены.

## Проверка

Из корня репозитория:

```sh
python -m unittest discover -s services/api/tests -v
```

Для интеграционных тестов задайте `TEST_DATABASE_URL` отдельной тестовой базы. Тесты создают и удаляют собственную уникальную схему. Без этой переменной интеграционные тесты пропускаются. CI предоставляет отдельный PostgreSQL service.

## Следующие этапы

2. Устойчивый worker, ограниченный пул соединений и индексы по измеренным запросам.
3. Миграции вместо DDL при запуске, разделение больших модулей.

Производственные данные не переписываются этим этапом; старые ошибочные решения о дублях требуют отдельной проверки.


# Этап 2: административный API

- Общая dependency защищает все непубличные API-маршруты, включая чтение промптов, исходных материалов и диагностики.
- Публичные лента, статьи, готовые прогнозы и health продолжают работать без секрета. Скрытая лента требует токен.
- Отсутствующий токен больше не отключает защиту: служебные запросы получают 503. Неправильный заголовок получает 403.
- Production проверяет наличие токена длиной минимум 32 символа до обращений к базе при старте.
- Studio отправляет токен при всех служебных чтениях. Cron/tick-скрипты загружают приватный .env и отправляют заголовок; отказы HTTP дают ненулевой exit code.
- Перед деплоем нужно проверить production токен и заменить прямые cron-вызовы curl на обновленные скрипты (см. README). Деплой этого этапа пока не выполнен.
- Все проверки локальные; новых вызовов AI API нет.

# Этап 3: worker и пул PostgreSQL

- Вместо daemon-потока API сохраняет pipeline job в PostgreSQL. Worker запускается отдельным процессом.
- Partial unique index ограничивает очередь одним активным заданием pipeline. Повторные отправки объединяются.
- Worker lock защищает от параллельных consumers; общая pipeline lock исключает пересечение с синхронными запусками.
- Задания имеют heartbeat, lease, owner, ограничение попыток, сохраненный результат и ошибку. Старый owner не может завершить задание после его передачи другому worker.
- API/worker startup сериализован. Восстановление статусов scheduler проверяет блокировки и не сбрасывает работающий этап.
- В админке отображаются фоновые задания. Cron ставит pipeline в очередь; синхронные endpoints сохранены.
- Добавлен ограниченный psycopg_pool с проверкой соединений, очисткой advisory locks, возвратом транзакций и закрытием при остановке.
- Проверены отдельный worker-процесс без AI, lease recovery, heartbeat, конкурентные consumers, лимит соединений, замена мертвого соединения и сохранность ранее выполненных сценариев.
- При деплое нужно пересобрать api, worker и web. На production этот этап пока не задеплоен.
- Обычная работа не добавляет AI-вызовов. Аварийное восстановление может повторить незавершенный вызов (максимум две попытки задания); exactly-once внешнего API не гарантируется.

# Этап 4: миграции и разделение кода

- SQL схемы перенесён в две неизменяемые версии: основная схема и очередь worker. Применение отдельной командой `python -m app.migrations upgrade`; `check` проверяет совместимость без DDL.
- Существующая база получает историю версий через прежний идемпотентный SQL. Сохранение материалов, заданий и настроек проверено на тестовой базе. Уже применённый SQL не повторяется.
- Контрольные суммы и последовательность истории защищают от изменённых, пропущенных или неизвестных версий. Advisory lock исключает конкурентное применение. При ошибке транзакция откатывает весь пакет вместе с историей.
- API и worker проверяют актуальность схемы. Compose содержит отдельный migration service и зависимости успешного завершения; локальный dev script обновляет схему до запуска API.
- Репозиторий разделён по областям, модели — по доменам. Существующие точки импорта и JSON schema всех моделей сохранены. Транзакции публикации и настройки пула не изменены.
- Большие `main.py`, `ingestion.py` и `ai_client.py` ещё требуют следующих этапов разделения; этот этап покрывает слой хранения и модели.
- Новых AI-вызовов и платных зависимостей нет. Production-деплой ещё не выполнен.

# Этап 5: разделение API, ingestion и AI-клиента

- `main.py` собирает FastAPI из шести HTTP-роутеров. Обработка запросов делегируется `service_*`; этапы планировщиков вынесены в `scheduler_*`, общая последовательность — в `pipeline.py`.
- `runtime.py` содержит общий экземпляр репозитория и константы лимитов/блокировок, `bootstrap.py` — инициализацию и lifespan. Worker обращается напрямую к bootstrap/pipeline, без импорта HTTP-приложения.
- Ingestion разделён на сбор, фильтрацию, scoring, probing, enrichment, сетевой доступ, RSS/Atom, sitemap, scraping, AI discovery и разбор статей. `ingestion.py` сохраняет прежние экспорты.
- AI-клиент разделён на транспорт и операции редактора, прогнозов, гайдов и источников, со вспомогательными модулями обработки ответов, текста и поиска. `OpenAIEditorialClient` и типы результатов остаются в прежней точке импорта.
- Сверены AST всех 122 функций/классов ingestion, 21 метода AI-клиента, 33 вспомогательных определений AI и 100 функций API/обработки. Поведение сохранено; удалён только ранее недостижимый фрагмент после `return` в проверке русского текста.
- Полная OpenAPI-схема до и после совпала. Проверен импорт в обоих пространствах имён: `services.api.app` локально и `app` для Docker.
- Все 52 теста проходят с отдельным PostgreSQL. Новые fixtures проверяют RSS/Atom, фильтрацию устаревших новостей, query-параметры, метаданные/текст HTML, payloads обоих AI API styles, citations/usage и прежний предел transport retry. Сеть AI подменена; платные запросы не выполнялись.
- Промпты, модели, лимиты web search, размеры партий и число AI-запросов не менялись. Новых миграций для этого этапа нет. Production-деплой ещё не выполнен.
